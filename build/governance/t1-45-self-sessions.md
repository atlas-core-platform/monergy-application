## Scope and requirements

The approved AR-003 customer experience includes security/sessions under Settings; COV-003 and COV-006 trace to MON-ID-006/012. This unit implements the current customer's own recorded session activity and explicit ending of a selected other session. It does not invent public registration, tenant ownership, agreement wording, verified devices/locations, failed-login history, MFA or retention/closure policy. MON-ID-006/012 remain partial; other Settings and full registration/agreement journeys remain open.

`/settings/sessions` is a protected customer destination. It shows start/expiry times, Active/Ended/Expired/Access changed status and a Current session label. Device/location information is truthfully unavailable. Lists are bounded to 100 records with exact owner-scoped cursor pagination and explicit latest/reload controls. Ending another active session requires confirmation, an opaque operation UUID, an exact target/operation receipt and a fresh owner read showing that target Ended. Current-session termination uses the existing Sign out flow. Pending mutations cannot be submitted twice. Conflicting/unconfirmed results block further changes until explicit reload; old responses are suppressed across tenant/actor/customer/session/API changes or unmount.

## Owner/security/persistence

C&I owns GET `/local/v1/me/sessions` and POST `/local/v1/me/sessions/revoke`. Trusted headers determine tenant/session; current AM membership and session authority determine the actor. This is intrinsic self-service identity control, not an administrative/business grant or a customer role/Consent mutation. Exactly the current actor is used in every database list, cursor and revocation predicate. Unknown JSON scope fields and foreign origins reject. Only one-way stored session references leave the owner; bearer session credentials are never returned in list/receipt data.

The tenant-local PostgreSQL repository uses the existing trusted-session/AM-consumption advisory lock and rechecks/locks the current session row before revocation, using the existing UPDATE(revoked) column privilege. It cannot update subject versions/expiry or resurrect a session. Selected target revocation and insertion into append-only runtime `self_session_receipts` commit together; failure rolls back both. Operation replay for the same actor/target returns its receipt; conflicting reuse rejects. Missing/foreign targets share the same not-found result. Current-session targets reject before mutation in both application and adapter. Current membership/session is rechecked after asynchronous owner calls; a post-commit denial does not claim rollback or a distributed AM transaction.

Migration `0006_self_session_receipts.sql` adds receipts and an actor/time/session history index. Runtime receives INSERT only on receipts, existing SELECT grants and existing revoked-column update authority. Hash-checked additive migration overlay, existing bootstrap/provisioning, Gateway and direct-route wiring are included. SHA256: `af2b3340eafd8fa24482f2f3ac648094bba0912b60a8bf14eed671649a141f02`.

The row-lock permission design follows PostgreSQL's documented requirement for SELECT plus UPDATE on at least one table column: https://www.postgresql.org/docs/16/ddl-priv.html . This is source design review, not executed database evidence.
