## Complete customer journey

Organization Settings > Customers lists named customers and registered email/secondary detail, availability and a customer-details action. Literal case-insensitive name/email/detail/reference search, Active/Inactive filters, server-side50-item cursor pagination, first-page navigation, refresh and tenant-wide total/active/inactive plus search-match counts are implemented. Counts and rows use one repeatable-read transaction in PostgreSQL. Empty and unavailable results remain distinct; a partial page is never presented as the entire matching directory.

Customer details show only customer name, registered email, secondary label, customer reference, availability and whether an owner link is recorded. No financial records, documents, PAN, date of birth, credentials, ownership evidence or customer impersonation are exposed. Existing People, Customer Assignments, public registration/KYC and customer-controlled Consent remain separate journeys.

An administrator explicitly reviews the named customer, records a nonblank one-line reason (up to500 characters) and confirms suspension/reactivation. Suspension stops customer workspace access without deleting data/history or changing the verified ownership record. Reactivation restores availability only when the underlying identity owner permits it; it cannot create an owner link, bypass membership/role/Consent checks or activate an ambiguous owner with another active customer. Changed customer-context versions invalidate stale authorization/Consent snapshots; no previously invalidated sharing approval is fabricated or automatically restored.

Each change requires the exact expected effective customer version. Stale edits, no-op changes, changed-payload operation reuse, reuse for another customer/administrator and unavailable activation reject. Repeated identical operations return the exact original before/after receipt, even after later status changes. Concurrent changes serialize on operation/customer locks, with an additional shared-owner lock for reactivation ambiguity checks. History is append-only, paged by exact resulting version and preserves reason, actor, recorded administrator email label, before/after metadata, operation and server time. Administrators can reopen details and earlier changes after suspension or reactivation.

The UI retains the same operation, expected version, target status, customer and reason when confirmation is uncertain, through close/reopen and reauthentication by the same tenant/actor. Another change is blocked until confirmation. The exact saved receipt is read back before success is shown.400 permits editing;409 requires current refresh and explicit review. Tenant/actor/session changes hide prior data and discard late responses. Recovery data remains in scoped process memory, with no browser-storage persistence or session credential copying.

## Owner and availability boundary

Customer & Identity owns the administrative metadata and availability lifecycle. Existing verified ownership remains in the read-only `customer_identity.customers` table; runtime INSERT/UPDATE/DELETE on that table is not granted. Additive migration0010 creates `customer_availability`, immutable `customer_status_changes` and a read-only `current_customers` owner view. Effective availability is original-owner active AND administrator availability; effective version is original-owner version plus availability version. Suspension/reactivation cannot reactivate a source-inactive identity or overwrite ownership.

Every existing C&I owner read in customer context/directory, self profile, email access, agreement acceptance and protected PAN uses the effective owner view, including ownership rechecks. This keeps administration independent of financial access and stops inactive customer entry and owned-customer operations. Runtime grants allow availability INSERT/UPDATE and status-history INSERT only. Delete/truncate on availability/history, update on history and all ownership mutations remain denied. Local UAT/bootstrap and AM05 grant scripts include the new tables. Existing tenant-specific databases and tenant-identity validation are retained; no shared tenant table is introduced.

GET `/local/v1/administration/customers` supports search/status/after. GET `/{customerId}` returns metadata; GET `/{customerId}/history?beforeVersion=` returns paged status history; GET `/{customerId}/changes/{operationId}` confirms an exact saved receipt; POST `/{customerId}/status` accepts operationId/expectedVersion/active/reason. The existing Gateway allowlist exposes only matching `/identity-api` methods/routes. It does not add a financial ingress or customer impersonation path.

Every read/write requires current AM Organization Administrator context, operator-bound tenant database and current trusted session. Authorization is checked before repository access, reconfirmed immediately before a mutation and reconfirmed afterward against exact tenant/actor/policy/authority. No new access permission or default role grant is invented. No-store/same-origin controls, strict16KiB JSON, exact constructor fields, duplicate/missing/unknown/null rejection and bounded query validation apply. Receipts bind the complete unchanged customer metadata, exact transition/version, current actor, operation and reason; fresh saved receipt readback must match. Forged metadata/results fail closed. Current authority loss after commit leaves an immutable receipt available for exact recovery after authority is restored.
