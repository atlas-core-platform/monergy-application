Goals express intended objectives. They do not become source-derived financial facts, assets, liabilities, income, expenses or verified balances. No source document is required or fabricated. Amounts and currency are entered explicitly; amounts are bounded to 999999999999.99 with two decimal places, currency is three uppercase letters, name is bounded to 120 characters without controls and target dates span 1900–2199. Past target dates remain representable without inferring overdue, active, completed or achieved status. Declaration status remains CUSTOMER_DEFINED. Editing currency changes the saved objective rather than converting the amount; no FX or aggregation is performed.

Financial Profile owns GET/POST /local/v1/customers/{customerId}/financial-goals, GET /{financialGoalId}, POST /{financialGoalId}/corrections and GET /{financialGoalId}/history, with matching /product-api/v1/financial-goals routes. Exact version reads and descending contiguous history retain each saved name, amount, currency, target date, actor, operation and timestamp. Latest lists are bounded to 200 unique goals; history is bounded to 50 versions with an explicit cursor and version-1 tail.

Current owned customer/session, operator customer-to-tenant binding and matching Self profile.read access are required. Writes additionally require current profile.update with matching actor/subject/customer versions. Document authority is unnecessary for a customer-defined objective. Strict 32 KiB ingress rejects missing, unknown, duplicate, null and invalid input. Product responses bind normalized complete target terms, customer, operation, actor, declaration status and exact version; fresh exact saved-version readback and current session/customer/authority reconfirmation follow each write. Forged lists, receipts, readbacks and history fail closed. Read-only access remains usable.

Migration 0021_customer_financial_goals.sql adds append-only relational goals and revisions with a composite customer/tenant/goal FK. Scoped operation fingerprints/identities, transaction/advisory locks and saved creation/revision receipts prevent changed-payload reuse, cross-record reuse, stale/competing writes and accidental duplicate goals. Replaying the original creation or edit returns that original saved version after later changes. Runtime SELECT/INSERT grants exclude UPDATE/DELETE. No new package, service, provider, GitHub Actions or production deployment.

Financial information > Financial goals is available even before document-derived source figures exist. Goal-only routes do not request the source profile or document endpoints. Forms start with blank amount/currency/date. Details and history show Customer defined and explicitly state that progress, contributions and achievement are not calculated. A confirmed 400 permits corrections; 409 freezes the form for refreshed review. Uncertain saves keep exactly the same operation, terms and expected version through retry/close/reopen.
